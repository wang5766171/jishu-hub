# jishu-task-conductor 详细设计评审意见

> 评审对象：`jishu-task-conductor_详细设计.md`  
> 评审日期：2026-06-24  
> 评审目的：判断该方案能否作为 Jishu Hub 最终任务执行机制，并指出必须修正的边界、事实偏差和落地风险。

---

## 0. 总体结论

这版方案的方向是正确的：它抓住了旧方案不稳定的根源，即阶段推进不应继续依赖前端关键词、外置脚本、技能话术或模型自觉，而应放到更靠近模型循环的派（Pi）原生扩展机制里。

但当前设计稿不能直接定为“无误”。它还需要修正几个硬边界：

1. **流程指挥器适合管对话阶段，不适合管任务事实。**
2. **中枢（Hub）的任务实例、任务图版本、执行运行、任务事件仍必须是权威状态。**
3. **外部执行器不能被描述成“流程指挥器直接调用另一个派工具”，因为当前派扩展接口没有直接调用注册工具的能力。**
4. **执行阶段不能让派工具长时间阻塞等待全部任务完成，应启动中枢执行运行后立即返回运行标识。**
5. **人工确认、产物路径、工具门、结构化计划、单会话分段等细节必须补齐，否则会把旧方案的不稳定换成新的双状态和长运行风险。**

因此，本评审建议将该方案调整为：

> **派扩展管“阶段怎么走”；中枢任务系统管“事实是什么”。**

只要这个边界改清楚，该方案可以成为最终任务机制的基础。

## 1. 我对需求的理解

你的真实诉求不是简单替换一个脚本，也不是给现有任务页面换一套技能文本，而是要解决任务功能的结构性不稳定：

- 任务分为需求讨论、流程规划、流程执行三个阶段。
- 每个阶段都和智能体对话有关，但不能让阶段推进完全依赖智能体自然语言。
- 任务执行本身很复杂，需要不同智能体、不同业务场景、不同产物形态共同参与。
- 任务执行阶段必须有一个持续运行的主进程，不能依赖某个主会话是否还活着。
- 规划产物需要能转换为任务图，由编排器调度，而不是让主聊天会话线性执行。
- 不同业务领域应能通过外挂方法包和执行器适配，而不是把所有业务写死在中枢或派核心里。

所以，新方案要解决的是：

> **把不稳定的阶段推进收口到派原生扩展，把复杂且可变的业务执行下沉到中枢执行器和任务编排层。**

这个方向和旧的 `advance_phase.mjs` 方案相比，确实更接近最终架构。

## 2. 名称解释

为避免文档全是英文名，下面给出本评审使用的中文名称。

| 中文名称 | 原设计名称 | 解释 |
|---|---|---|
| 派 | Pi | Jishu Agent 底层使用的智能体运行时，提供原生扩展、工具、会话、模型循环能力。 |
| 中枢 | Hub | Jishu Hub 桌面应用和后端，负责图形界面、任务数据库、编排器、运行时适配和事件投影。 |
| 流程指挥器 | Conductor | 跑在派里的扩展代码，负责阶段推进、方法注入、工具门和会话内恢复。 |
| 方法包 | skill pack | 每个领域的一组方法论文件，例如开发领域的需求讨论方法、规划方法、执行方法。 |
| 外部执行器 | jishu-task-executor | 连接流程指挥器与中枢任务编排器的执行入口。设计上应负责把计划交给中枢启动执行运行。 |
| 任务实例 | TaskInstance | 中枢任务列表中的核心对象，表示一个任务的生命周期、当前阶段、关联产物和执行状态。 |
| 任务图 | TaskGraph | 任务的图结构身份，保存目标和当前草稿或图定义。 |
| 任务图版本 | GraphRevision | 经过校验后的不可变任务图快照，执行时应绑定某个明确版本。 |
| 执行运行 | GraphRun | 某个任务图版本被真正启动后的一次执行。一个图可以执行多次。 |
| 节点执行 | NodeRun / NodeAttempt | 任务图里某个节点的执行状态与具体尝试。每次尝试可以绑定不同智能体会话。 |
| 任务事件 | TaskEvent | 编排器追加记录的运行事实，例如节点开始、完成、失败、审批、返工。 |
| 会话附记 | appendEntry | 派会话里的自定义持久化记录，适合恢复扩展状态，但不应作为中枢任务事实的唯一来源。 |

## 3. 核心判断展开

### 3.1 流程指挥器适合做什么

流程指挥器最适合处理“对话阶段纪律”。

原因是它运行在派内部，靠近智能体模型循环，可以在每一轮对话前后介入：

- 在模型开始前注入当前阶段的方法论。
- 在需求阶段禁止写文件或执行危险工具。
- 在规划阶段要求输出结构化计划。
- 在阶段收敛时触发人工确认。
- 在会话恢复时读取会话附记，恢复当前阶段。
- 在上下文压缩后重新把当前阶段规则注入模型。

这些能力正好击中旧方案的问题。旧方案中，前端需要猜模型是不是“完成需求讨论”，脚本需要模型记得调用，技能文本需要模型长期遵守。流程指挥器把这些从“约定”变成“运行时机制”，这是架构上更稳的地方。

### 3.2 流程指挥器不适合做什么

流程指挥器不适合成为任务系统的权威状态源。

派会话是智能体会话，不是任务数据库。它可以帮助恢复一次对话里的阶段，但不能回答完整的任务事实问题：

- 这个任务是否还在执行。
- 当前活跃的是哪一次执行运行。
- 哪个任务图版本正在跑。
- 哪些节点完成、失败、等待审批。
- 哪些智能体实际参与了节点执行。
- 应用重启后任务列表如何快速显示状态。
- 历史执行事实如何重放和审计。

这些都应由中枢的任务实例、任务图版本、执行运行和任务事件来承载。

所以，流程指挥器的定位应是：

> **对话阶段驱动器，而不是任务事实数据库。**

### 3.3 中枢仍是任务生命周期权威

顶层工程文档已经明确：任务系统的权威模型是任务图、任务图版本、执行运行、节点执行和任务事件，而不是可变计划文档或线性步骤。

因此，新方案不能把任务生命周期整体迁到派会话里。正确边界应是：

| 阶段 | 派流程指挥器负责 | 中枢任务系统负责 |
|---|---|---|
| 需求讨论 | 约束对话、引导澄清、提交需求产物 | 创建或更新任务实例，保存需求产物引用 |
| 流程规划 | 注入规划方法、要求提交结构化计划 | 校验计划，生成任务图版本候选 |
| 用户确认 | 发起确认交互 | 保存确认结果，创建不可变任务图版本 |
| 流程执行 | 触发执行入口，进入监督视角 | 启动执行运行，调度节点，记录任务事件 |
| 执行监控 | 辅助监督、解释进展、接受用户干预 | 持续运行主进程，维护运行事实和投影 |

这一点必须写进最终设计，否则会形成两套状态：派会话里一套，中枢数据库里一套，后续一定会产生不同步问题。

### 3.4 外挂机制的合理边界

“方法包 + 外部执行器”这个分层是对的。

方法包负责不同领域的思考方式，例如开发任务、调研任务、文档任务。它改变的是提问方式、规划口径、验收标准，而不是中枢的调度规则。

外部执行器负责不同环境的执行方式，例如中枢环境用任务编排器，纯派命令行环境用单智能体兜底。它改变的是计划如何被消费，而不是阶段协议本身。

这个分层保留了扩展性：

- 流程指挥器保持领域无关。
- 方法包按领域替换。
- 执行器按运行环境替换。
- 中枢编排器保持任务事实权威。

## 4. 当前方案解决了什么

这版方案相对旧方案有明显进步。

### 4.1 解决前端猜意图问题

旧方案中，前端曾经通过关键词判断用户是否确认生成流程图。这种方式天然不稳定，换一种说法就可能误判。

新方案把阶段推进放到派扩展里，由流程指挥器在智能体回合结束后判断产物和状态，再走人工关卡。这比前端猜文本更可靠。

### 4.2 解决脚本散落问题

旧方案让智能体调用 `advance_phase.mjs` 推进阶段，本质是把关键状态转换放在外挂脚本里。脚本能跑，但路径、环境变量、会话标识和错误处理都容易成为不稳定点。

新方案用派原生扩展承载阶段机，能减少脚本层的漂移。

### 4.3 解决方法论和机制混杂问题

旧的任务技能既写方法论，又写推进方式，还带脚本调用说明，容易让模型混淆。

新方案把机制放到流程指挥器，把方法论放到方法包，边界更清楚。

### 4.4 解决执行阶段单会话承载过重问题

设计稿已经意识到执行阶段不应由主会话单独完成，而应交给中枢编排器，多智能体节点会话独立执行。这一点符合任务系统长期方向。

## 5. 阻塞性问题

以下问题不修正，不建议直接把该方案作为最终机制。

### 5.1 阻塞问题一：流程指挥器不能成为任务事实权威

设计稿中有一条倾向：Hub 任务列表从流程指挥器的会话附记读取阶段。这个做法只能作为临时投影，不能作为最终权威。

原因：

- 会话附记属于派会话文件，不属于中枢任务数据库。
- 任务列表需要独立于会话读取快速展示。
- 执行运行和节点状态来自编排器，不来自主会话。
- 应用重启、会话压缩、分叉、删除、迁移时，会话附记不能承担所有事实。

建议改为：

- 流程指挥器每次阶段变化都可以写会话附记，供派恢复。
- 同时必须通过中枢任务接口更新任务实例。
- 任务列表、工作台、执行态只读任务实例和任务事件投影。
- 会话附记只能作为“派侧恢复状态”，不是“中枢权威状态”。

### 5.2 阻塞问题二：当前派扩展接口不能直接调用另一个注册工具

设计稿多次写到：流程指挥器在执行阶段直接调用 `jishu-task-executor` 工具。

但根据当前派扩展接口，扩展可以：

- 注册工具，让模型调用。
- 查看工具信息。
- 注入消息。
- 发送用户消息或自定义消息。
- 执行 shell 命令。

但扩展接口没有暴露“按工具名直接调用某个注册工具”的能力。也就是说，流程指挥器不能像普通函数一样直接调用另一个扩展注册的工具。

这会影响核心链路：

```text
流程指挥器 -> 直接调用外部执行器工具 -> 中枢启动执行
```

这条链路按当前接口并不成立。

可选修正方案：

1. **模型中介方案**：流程指挥器进入执行阶段后，注入明确消息，要求模型调用外部执行器工具。优点是改动小，缺点是仍有模型执行不确定性。
2. **统一转移工具方案**：由流程指挥器自己注册 `commit_plan` 或 `start_execution` 工具，模型调用该工具后，工具内部通过中枢本地接口或命令启动执行。优点是转移点明确，缺点是需要定义派扩展到中枢的稳定桥接。
3. **扩展服务接口方案**：为派 fork 增加最小 API，例如“扩展可调用命名服务”。优点是机制干净，缺点是会增加派 fork 改动，违反“尽量复用原生能力”的原则。

推荐第二种：把关键阶段转移收口到流程指挥器自有的结构化工具中，而不是让一个扩展直接调用另一个扩展工具。

### 5.3 阻塞问题三：外部执行器不应阻塞到全部执行完成

设计稿中写外部执行器读取计划、转任务图、启动编排器，然后等待全部完成后返回给流程指挥器。

这不适合作为最终机制。

原因：

- 执行可能持续很久，派工具调用不应长时间悬挂。
- 应用重启、取消、暂停、恢复都不应依赖一个未返回的工具调用。
- 编排器是持续主进程，不能被包进一次智能体工具调用生命周期。
- 用户进入执行工作台后，进度来自任务事件，而不是工具调用结果。

建议改为：

```text
流程指挥器进入执行阶段
  -> 提交已确认计划
  -> 中枢创建任务图版本
  -> 外部执行器启动执行运行
  -> 外部执行器立即返回 run_id
  -> 流程指挥器记录“已启动执行”
  -> 中枢编排器持续调度
  -> 界面通过任务事件投影显示进度
```

执行完成后，流程指挥器可以收到或查询完成摘要，但不应作为执行主进程。

### 5.4 阻塞问题四：`ctx.ui.confirm` 在中枢侧映射不完整

设计稿写人工关卡使用 `ctx.ui.confirm`，并认为中枢侧已经可用。

但当前中枢的派协议转换只把 `select` 和 `input` 转为交互请求，`confirm` 被归为不映射或忽略的类型。

这意味着，如果流程指挥器调用 `ctx.ui.confirm`，中枢界面未必能收到可回应的交互请求。

修正方案：

- 方案一：补齐中枢对 `confirm` 的映射，转成带“确认 / 取消”两个选项的交互请求。
- 方案二：流程指挥器统一使用 `ctx.ui.select` 表达确认，例如“批准进入下一阶段 / 返回修改”。

推荐方案二作为短期方案，因为它复用现有已验证通道。长期可以补齐 `confirm` 映射，保持派接口语义完整。

### 5.5 阻塞问题五：哨兵文本不能作为最终阶段转移条件

设计稿中保留了 `[REQUIREMENT LOCKED]`、`[STEP:n DONE]` 这类哨兵文本。

这适合示例和兜底，不适合最终机制。

原因：

- 哨兵仍然是自然语言输出的一部分。
- 模型可能漏写、写错、重复写。
- 用户或上下文中也可能出现相同文本。
- 多阶段、多计划、多次执行时，扫描边界容易出错。

建议最终机制中：

- 需求锁定使用 `lock_requirement` 结构化工具。
- 计划提交使用 `commit_plan` 结构化工具。
- 执行启动使用 `start_execution` 或等价结构化工具。
- 哨兵只用于纯派命令行兜底模式，不进入中枢最终路径。

### 5.6 阻塞问题六：结构化计划不应直接等同任务图版本

设计稿里的 `flow-plan.json` 是一个好边界，但不能直接作为任务图版本。

它应该被视为“计划提案”，原因：

- 它由模型生成，必须校验。
- 它缺少权限、预算、资源、审批、循环、失败策略等执行约束。
- 它的角色字段只是建议，不是最终智能体分配。
- 它不应绕过中枢的任务图版本校验。

建议改名和改义：

- `flow-plan.json` 可以保留为人机可读中间产物。
- 同时定义 `FlowPlanProposal` 或“流程计划提案”。
- 中枢把提案转换为任务图命令。
- 校验通过后生成不可变任务图版本。
- 执行运行必须绑定任务图版本，而不是绑定原始计划文件。

### 5.7 阻塞问题七：产物路径缺少任务命名空间

设计稿把需求产物和计划产物写为：

- `REQUIREMENTS.md`
- `flow-plan.md`
- `flow-plan.json`

如果直接落在工作目录，会出现问题：

- 多任务互相覆盖。
- 任务分叉后产物不易区分。
- 历史计划和当前计划无法追溯。
- 执行运行无法绑定具体产物版本。

建议统一落到任务工作区，例如：

```text
.jishu-hub/tasks/<task_id>/
  artifacts/
    requirements/
      requirements.md
      manifest.json
    planning/
      flow-plan.md
      flow-plan.json
      manifest.json
```

`manifest.json` 至少记录：

- 产物标识。
- schema 版本。
- 内容哈希。
- 生成阶段。
- 生成会话。
- 关联任务实例。
- 关联任务图版本或候选版本。

### 5.8 阻塞问题八：工具门必须从禁用名单改为阶段白名单

设计稿中主要写禁用 `edit/write`，再通过工具调用事件兜底。

这还不够。

原因：

- `bash` 可以写文件。
- 自定义工具可能修改文件或发起网络请求。
- 模型上下文中可能出现其他扩展工具。
- 后续接入模型上下文协议工具后，工具能力更复杂。

建议每个阶段定义明确白名单：

| 阶段 | 工具策略 |
|---|---|
| 需求讨论 | 只允许只读工具、用户提问工具、必要的结构化提交工具 |
| 流程规划 | 只允许只读工具、计划提交工具、必要的用户确认工具 |
| 流程执行 | 由中枢任务编排器按节点角色和权限策略决定 |

同时要求所有未知工具默认不可用，必须显式加入当前阶段白名单。

### 5.9 阻塞问题九：单会话模型需要和任务多会话需求重新对齐

设计稿选择需求讨论、流程规划、执行监督都在同一个派主会话中，用阶段标记和界面分段查看。

这个选择有合理性，因为它能减少跨会话串联问题。但它与早期任务原型中“不同阶段不同聊天标识，点击阶段切换”的需求存在差异。

建议明确最终取舍：

- 需求讨论和流程规划可以是同一个主会话的两个阶段视图。
- 执行监督可以是同一个主会话的执行阶段视图。
- 节点执行仍然必须是独立节点会话。
- 界面上仍要保留阶段切换，但它可以是逻辑分段，而不是物理会话切换。

如果产品上仍要求需求和规划是不同真实会话，则本方案的“单会话连续”需要重做。按稳定性优先，本评审建议接受单主会话，但文档必须明确该取舍。

### 5.10 阻塞问题十：外部执行器和兜底执行器的注册关系不清

设计稿说中枢注册外部执行器，没人注册时流程指挥器使用内置兜底。

但派扩展工具按名称注册时，如果多个扩展注册同名工具，会涉及加载顺序和覆盖规则。当前扩展注册工具并不是一个清晰的“服务发现总线”。

建议：

- 不要让外部执行器和兜底执行器注册同一个工具名并依赖加载顺序。
- 明确区分中枢环境和纯派环境。
- 在中枢环境中，由流程指挥器通过稳定中枢桥接启动执行。
- 在纯派环境中，才进入单智能体兜底流程。

## 6. 建议的最终机制

下面是本评审建议的最终任务机制。

### 6.1 总体模型

```text
用户创建任务
  -> 中枢创建任务实例
  -> 启动派主会话并启用流程指挥器
  -> 需求讨论阶段
  -> 锁定需求工具提交需求产物
  -> 用户确认进入规划
  -> 流程规划阶段
  -> 提交计划工具提交计划提案
  -> 中枢校验并生成任务图版本候选
  -> 用户确认执行
  -> 中枢启动执行运行
  -> 编排器持续调度节点
  -> 界面通过任务事件显示进度
```

### 6.2 需求讨论阶段

流程指挥器负责：

- 注入需求澄清方法。
- 限制工具为只读和用户交互。
- 引导模型每次只问一个核心问题。
- 在模型认为需求收敛时，要求调用“锁定需求”工具。

锁定需求工具负责：

- 接收结构化需求正文。
- 写入任务产物目录。
- 计算内容哈希。
- 通知中枢任务实例进入“需求已锁定待确认”状态。

用户确认后：

- 中枢任务实例进入规划阶段。
- 流程指挥器切换到规划阶段。

### 6.3 流程规划阶段

流程指挥器负责：

- 注入规划方法。
- 要求读取需求产物。
- 限制写操作。
- 引导模型生成节点、依赖、角色、验收标准。
- 要求调用“提交计划”工具。

提交计划工具负责：

- 接收计划提案。
- 校验基础 schema。
- 写入计划产物。
- 交给中枢转换为任务图命令。

中枢负责：

- 校验有向无环图。
- 校验角色和能力要求。
- 校验权限、预算、资源和审批策略。
- 生成任务图版本候选。
- 给用户展示差异和风险。

用户确认后：

- 候选变为正式不可变任务图版本。
- 任务实例进入执行准备或执行阶段。

### 6.4 流程执行阶段

流程指挥器负责：

- 进入执行监督阶段。
- 触发或确认执行启动。
- 注入监督方法论，例如如何看进度、何时建议返工、何时请求用户干预。
- 不亲自执行节点。

中枢外部执行入口负责：

- 基于任务图版本启动执行运行。
- 返回执行运行标识。
- 不等待全部执行完成。

中枢编排器负责：

- 作为持续主进程运行。
- 按依赖释放节点。
- 按角色和能力选择智能体。
- 管理节点执行、重试、审批、预算和取消。
- 将运行事实写成任务事件。
- 维护执行工作台投影。

主会话监督视图负责：

- 展示任务事件摘要。
- 接收用户 steer。
- 必要时让 jishu agent 进行语义评估或返工建议。

节点会话负责：

- 每个节点的真实智能体执行。
- 保存节点尝试会话。
- 支持用户进入节点细看和干预。

## 7. 与原设计稿的具体修改建议

### 7.1 修改设计定位

原文：

> Conductor 只管三件事，阶段推进、产物契约、产物串联。

建议改为：

> 流程指挥器只管派主会话内的阶段纪律、产物提交入口和方法注入。任务实例状态、任务图版本、执行运行和任务事件由中枢任务系统作为权威事实管理。

### 7.2 修改执行器契约

原设计的出参：

```ts
{
  status: "completed" | "failed" | "partial",
  completedSteps: string[],
  summary?: string,
  error?: string
}
```

建议改为启动型结果：

```ts
{
  status: "started" | "failed",
  taskId: string,
  graphId: string,
  revisionId: string,
  runId?: string,
  summary?: string,
  error?: string
}
```

后续完成状态从任务事件和执行运行状态读取，不通过该工具返回。

### 7.3 修改产物契约

建议将 `flow-plan.json` 明确为计划提案，而不是最终任务图。

至少增加字段：

```jsonc
{
  "schema": "jishu-flow-plan-proposal/v1",
  "task_id": "...",
  "domain": "dev",
  "goal": "...",
  "requirements_artifact": {
    "path": "...",
    "content_hash": "..."
  },
  "nodes": [],
  "constraints": {
    "budget": null,
    "approval_policy": null,
    "max_parallelism": null
  },
  "generated_by": {
    "session_id": "...",
    "skill_pack": "...",
    "skill_pack_hash": "..."
  }
}
```

### 7.4 修改人工关卡

短期建议不用 `confirm`，统一用选择交互：

```text
请选择下一步：
1. 批准进入下一阶段
2. 返回继续修改
3. 取消任务流程
```

这样可以复用当前中枢已支持的 `select` 映射。

### 7.5 修改阶段转移条件

最终机制中不应写“回复带哨兵即可转移”。应写：

- 需求阶段通过 `lock_requirement` 工具提交。
- 规划阶段通过 `commit_plan` 工具提交。
- 执行阶段通过中枢启动执行运行。
- 哨兵只作为纯派兜底模式使用。

### 7.6 修改任务列表读取方式

原设计说任务列表可从会话附记读取阶段。

建议改为：

- 任务列表读取任务实例表。
- 会话附记只帮助派主会话恢复阶段。
- 如果会话附记和任务实例不一致，以任务实例为准，并由流程指挥器在下次会话开始时自我修正。

## 8. 分阶段落地路线

### 第一阶段：流程指挥器骨架

目标：证明派扩展能稳定驱动需求讨论和规划阶段。

范围：

- 注册启动命令或由中枢启动时注入流程上下文。
- 实现阶段状态。
- 实现方法包注入。
- 实现阶段白名单工具门。
- 实现 `lock_requirement` 和 `commit_plan` 两个结构化工具。
- 人工确认使用选择交互。

不做：

- 不启动真实编排器。
- 不做多领域。
- 不做长运行执行。

### 第二阶段：中枢任务实例对接

目标：消除派会话状态和中枢任务状态双写风险。

范围：

- 任务开始时绑定任务实例标识。
- 需求产物写入任务目录。
- 计划产物写入任务目录。
- 阶段变化同步任务实例。
- 任务列表只读任务实例。

### 第三阶段：计划提案到任务图版本

目标：让规划产物进入正式任务图模型。

范围：

- 定义计划提案 schema。
- 中枢校验计划提案。
- 转换为任务图命令。
- 生成任务图版本候选。
- 用户确认后固化不可变任务图版本。

### 第四阶段：启动执行运行

目标：从“提交计划”进入真正的执行工作台。

范围：

- 基于任务图版本启动执行运行。
- 返回执行运行标识。
- 任务实例记录活跃执行运行。
- 编排器持续调度节点。
- 前端切换执行工作台。

### 第五阶段：监督和返工

目标：让 jishu agent 成为监督者，而不是执行主进程。

范围：

- 主任务会话投影任务事件。
- 用户可对主运行或节点进行干预。
- 监督者可提出返工建议。
- 返工必须形成受限计划提案或新任务图版本，不能静默改历史。

## 9. 验收标准

该方案进入最终机制前，至少应满足以下验收点：

1. 前端不再通过关键词判断阶段完成。
2. 阶段推进不再依赖 `advance_phase.mjs`。
3. 需求和计划提交是结构化工具调用。
4. 任务列表状态来自任务实例，不来自解析会话文本。
5. 派会话恢复依赖会话附记，但中枢事实不依赖会话附记。
6. 计划提案必须经中枢校验后才能成为任务图版本。
7. 执行运行启动后，派工具不长时间阻塞等待完成。
8. 编排器在主会话关闭后仍能继续执行。
9. 执行进度来自任务事件投影。
10. 节点执行会话仍然可独立查看。
11. 人工确认使用当前中枢确实支持的交互通道，或补齐缺失映射。
12. 工具门是阶段白名单，不是简单禁用个别工具。
13. 多任务并行时产物不会互相覆盖。
14. 分叉或恢复时，任务实例和派会话状态有明确冲突解决规则。

---

## 10. 最终建议

这份设计稿可以作为最终任务机制的基础，但建议先做一次“边界修订版”，不要直接进入实现。

修订版应重点改四句话：

1. **流程指挥器不是任务生命周期权威，只是派主会话阶段驱动器。**
2. **中枢的任务实例、任务图版本、执行运行、任务事件是最终事实来源。**
3. **外部执行入口负责启动执行运行并返回运行标识，不负责阻塞等待全部完成。**
4. **阶段转移通过结构化工具和中枢校验完成，哨兵文本只作为兜底。**

改完后，这条路线是合理的。它能保留派原生扩展的稳定性，又不破坏中枢任务编排的权威模型。
