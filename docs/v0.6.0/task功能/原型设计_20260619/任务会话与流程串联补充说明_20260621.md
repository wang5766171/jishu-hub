# 任务会话与流程串联补充说明

> 日期：2026-06-21  
> 来源：任务 UI 实现反馈与需求讨论沉淀  
> 关系：补充 `任务UI美化设计方案_20260619.md`、`任务会话核心复用审查说明_20260620.md` 与 `任务UI美化实施计划_20260619.md`  
> 状态：作为后续任务模式、任务会话、流程创建和执行监控的实现约束

## 1. 背景

本轮实现反馈中确认，任务 UI 的关键问题不是单纯“页面不够美观”，而是任务发起、需求讨论、流程创建、流程执行之间的产品逻辑和会话复用边界必须重新收紧。

用户明确要求：

- 任务发起前不是表单填写，而是像常规会话一样先通过真实智能体会话澄清需求。
- 任务会话必须复用常规会话核心能力，包括交互式问答、引导发送、工具渲染、流式输出、停止/中断和消息区域渲染。
- 任务生成前的确认、审阅和引导不应使用割裂的弹窗，而应嵌入任务会话。
- 任务生成后进入流程页面时，应和原型及主题保持一致，能够清晰查看节点职责、关系、执行情况和节点会话。
- 任务模式需要支持 Skill 驱动；所选 Skill 贯穿需求讨论、任务规划和任务执行。
- 需求讨论的最终结果必须形成固定目录下的需求终稿，流程创建阶段读取该终稿，而不是只把聊天上下文直接塞给流程创建逻辑。

## 2. 产品原则

### 2.1 会话优先

任务从会话开始，而不是从表单开始。  
任务模式的初始页面应尽量接近常规“新对话”体验，用户可以直接输入一句话，也可以通过多轮对话逐步澄清目标、范围、约束、验收标准和不希望智能体处理的事项。

### 2.2 真实复用

任务会话不能重新开发一套看起来类似的会话页面。  
任务模式必须直接复用常规会话核心链路，包括：

- `ChatInput` 输入框能力
- `MessageView` 消息渲染能力
- `StreamingMessage` 流式渲染能力
- `streamStore` 流式状态管理
- 交互式问答提交链路
- staged guide / 引导发送链路
- 工具调用和工具结果聚合渲染
- 停止、打断、继续交流能力

任务专属内容只能作为工具、slot、adapter 或按需组件挂载到共享会话能力上。

### 2.3 阶段连续

任务流程分为四个连续阶段，并且每个阶段都挂在同一个“任务实例”下：

1. 需求讨论：真实智能体会话，用户随时补充、打断和调整。
2. 需求定稿：将讨论结果整理为固定目录下的需求终稿。
3. 流程创建：读取需求终稿，生成可审阅的任务流程图。
4. 执行干预：在流程节点中查看执行内容，并通过节点会话随时引导和干预。

阶段之间不能依赖弹窗割裂，也不能只依赖临时内存上下文传递。

修订要求：

- 左侧任务会话列表以任务实例为基准收敛展示，一个任务实例只显示一条记录。
- 任务实例内部记录阶段会话，包括需求讨论会话、流程规划会话和后续执行/节点会话。
- 进入某个任务实例后，可以回溯查看需求讨论阶段，也可以查看流程规划阶段。
- 需求阶段结束后，不应先显示一个只有目标节点的流程图再要求用户点击“智能规划”，而应自动进入流程规划阶段会话。

### 2.4 Skill 驱动

任务模式不是固定的单一规划器，而应由任务规划 Skill 驱动。  
Skill 是贯穿任务生命周期的方法论和执行约束来源：

- 需求讨论阶段：告诉智能体使用所选 Skill 澄清需求，不做实施、不创建流程图。
- 流程创建阶段：使用同一 Skill 读取需求终稿并生成流程图。
- 任务执行阶段：使用同一 Skill 的角色、阶段和验收方法指导节点执行。

默认 Skill 为 `Jishu Task Planner`。其他 Skill 如 `Compound Engineering`、`GStack`、`OpenSpec`、`Superpowers` 可作为后续扩展项。

## 3. 任务初始页面要求

### 3.1 入口命名

侧边栏入口命名应简洁：

- `新对话`：进入常规会话模式。
- `新任务`：进入任务模式的新会话。

### 3.2 模式切换

会话输入框内增加模式选择：

- `会话模式`
- `任务模式`

切换模式的行为等同于点击侧边栏入口：

- 从会话模式切换到任务模式，等同于点击 `新任务`，进入一个新的任务会话。
- 从任务模式切换到会话模式，等同于点击 `新对话`，进入一个新的常规会话。
- 切换模式不是在当前会话内容上原地改变语义，避免普通会话和任务会话数据混杂。

当前从哪个入口进入，就默认显示哪个模式。

### 3.3 任务模式输入区

任务模式输入区应复用常规会话输入区的视觉和交互，只增加任务专属控制：

- 任务模式选择。
- 任务规划 Skill 选择。
- 权限选择。
- 项目和模型信息。
- Jishu Agent 状态。

任务模式不再保留独立的标题输入框、取消按钮或额外表单区。  
标题可由需求终稿或流程创建结果自动推导，后续如需修改，应在流程图或任务详情中编辑。

### 3.4 直接生成与需求讨论

任务模式支持两种使用方式：

| 方式 | 用户意图 | 行为 |
| --- | --- | --- |
| 需求讨论 | 需求还不明确，需要多轮澄清 | 消息进入真实智能体会话，智能体只做需求澄清和总结 |
| 直接生成任务 | 简单任务，一句话足够 | 用户发送后直接将该句话作为需求输入，进入流程规划阶段会话 |

是否需要讨论由用户判断。系统不应强迫用户必须先走多轮对话。

注意：直接生成任务不等于直接落地流程图。它跳过多轮需求澄清，但仍应进入“流程规划阶段会话”，由智能体基于一句话需求生成流程方案，用户可以继续打断、追问、修改和确认。

## 4. 任务会话与常规会话分离

任务会话和常规会话共享核心能力，但数据归属必须分离。任务数据归属以“任务实例”为中心，而不是以 session 为中心。

### 4.1 列表分离

侧边栏中应分别展示：

- 常规会话
- 任务会话

任务模式发起的会话不能跑到常规会话列表中。  
任务会话可以继续使用底层 session id，但需要额外记录其任务实例、阶段、Skill、需求终稿和最终 graph 信息，用于列表过滤、阶段回溯和后续流程创建。

任务实例建议包含：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 任务实例 ID |
| `title` | 任务标题，可重命名 |
| `skill_id` | 当前任务使用的规划 Skill |
| `status` | 当前状态，如需求讨论中、需求已定稿、流程规划中、流程已生成 |
| `current_phase` | 当前阶段，如 requirements、planning、graph |
| `requirement_session_id` | 需求讨论阶段会话 |
| `planning_session_id` | 流程规划阶段会话 |
| `requirement_file` | 需求终稿路径 |
| `graph_id` | 最终任务流程图 ID |

左侧列表展示 `TaskInstance`，而不是直接展示每个阶段 session。右键菜单至少支持：

- 重命名任务。
- 删除任务。

删除任务应清理任务实例、阶段索引、需求终稿目录，以及已生成的任务流程图数据。

### 4.2 渲染共享

分离的是数据归属和入口，不是渲染能力。  
任务会话仍应使用常规会话同一套消息渲染、输入框、流式状态和交互问答链路。

### 4.3 UI 专属能力按需挂载

任务模式可以额外挂载：

- Skill 选择器。
- 需求终稿确认卡。
- 生成任务流程图的交互卡。
- Proposal Diff。
- 任务图预览。
- 节点上下文条。

这些组件不应侵入常规会话核心。

## 5. Jishu Agent 与 Skill 约束

### 5.1 强制使用 Jishu Agent

任务模式必须自动切换到 `Jishu Agent`。  
如果用户未安装 Jishu Agent，应提示用户先安装，且任务模式不能继续发送。

原因：

- 任务模式需要固定的任务编排、需求定稿、流程创建和 orchestrator 能力。
- 普通常规 Agent 不一定具备任务规划工具和任务图生成工具。

### 5.2 Skill 选择器

任务模式下，在模式选择后增加任务规划 Skill 选择器。  
默认选中 `Jishu Task Planner`。

Skill 卡片应表达：

- Skill 名称。
- 安装状态。
- 简短说明。
- 是否可用。
- 未安装时的一键安装入口。

对于未安装 Skill，应弹出安装提示，后续可扩展安装方式：

- npm 安装。
- git 安装。
- 手动安装到指定目录。

### 5.3 需求讨论阶段的 Skill 提示

当用户选择某个 Skill 后，任务会话发送给智能体的系统性约束应包含：

```text
当前处于需求讨论阶段。
请使用所选任务规划 Skill 的方法论帮助用户澄清需求。
可以提问、总结、指出缺口、建议是否进入流程规划。
不要实施代码。
不要执行命令。
不要创建任务流程图。
不要输出最终执行计划。
当需求足够明确时，请向用户确认是否生成任务流程图。
```

该约束应作为任务模式的隐藏指令或工具约束注入，不应污染用户可见消息。

## 6. 需求终稿与流程创建串联

### 6.1 不能只传聊天上下文

需求讨论完成后，不能只把聊天上下文直接传给流程创建。  
流程规划阶段必须读取固定位置的需求终稿文件。

这样做的原因：

- 需求终稿可追溯。
- 流程图生成有稳定输入。
- 用户后续测试和复盘时可以查看当时依据。
- 多轮对话中的临时想法、反复修改和废弃方向不会混入最终规划。

### 6.2 需求稿目录

建议目录结构：

```text
<project-root>/.jishu-hub/tasks/<task-id>/requirements/
└── requirements.md
```

其中 `requirements.md` 应至少包含：

- 任务标题。
- 选用的任务规划 Skill。
- 目标说明。
- 范围边界。
- 约束条件。
- 验收标准。
- 用户明确排除的事项。
- 对话摘要或关键确认记录。
- 生成时间和来源 session id。

### 6.3 流程创建输入

流程规划阶段应接收的是“读取需求终稿并与用户讨论流程方案”的规划指令，而不是原始聊天记录。

示例：

```text
请读取以下需求终稿，并基于该需求与用户进行任务流程规划讨论：
<project-root>/.jishu-hub/tasks/<task-id>/requirements/requirements.md
```

流程规划阶段仍是会话模式：

- 智能体基于需求终稿生成流程方案。
- 用户可以继续打断、追问、修改节点职责、依赖和验收口径。
- 智能体可以发起交互式问答，确认是否生成任务流程图。
- 用户确认后，才生成 `TaskGraph`、`GraphRevision` 和可审阅 Proposal。
- 生成流程后进入任务画布/分屏页面。

### 6.4 生成入口

需求讨论阶段和流程规划阶段的生成入口都应来自会话内交互，而不是弹窗：

- 智能体判断需求明确后，给出“是否生成任务流程图”的交互选项。
- 在需求讨论阶段，用户确认后，前端调用需求定稿逻辑，并自动进入流程规划阶段会话。
- 在流程规划阶段，用户确认后，前端调用任务流程图创建逻辑。
- 用户也可以在直接生成任务模式下，一句话触发需求定稿，并自动进入流程规划阶段会话。

阶段流转如下：

```text
新任务
  → 需求明确阶段
      → 需求讨论：多轮真实会话 → Agent 整理需求 → 用户确认
      → 直接生成任务：一句话需求
  → 写入需求终稿
  → 自动开启流程规划阶段会话
      → Agent 基于需求终稿规划流程
      → 用户可打断、追问、补充
      → Agent 发起生成流程图确认
  → 用户确认后生成任务流程图
  → 进入流程画布 / 分屏执行监控
```

## 7. 流程页面与执行阶段要求

### 7.1 主题一致

流程页面必须和当前应用主题呼应。  
画布、节点、连线、状态标签、Inspector、任务会话区域都应使用统一 token，不应出现和前一阶段明显割裂的视觉风格。

### 7.2 节点职责与关系展示

生成任务后，应清晰展示：

- 每个节点的职责。
- 节点类型。
- 执行者或角色。
- 前后依赖关系。
- 控制依赖和数据依赖的区别。
- 当前运行状态。
- 是否需要用户审批或干预。

### 7.3 节点会话

任务执行过程中，用户可以进入任意节点查看执行内容。  
节点会话应尽量复用常规会话能力，至少在展示层保持一致：

- 消息流。
- 工具调用卡片。
- Thinking 的公开摘要边界。
- 交互式问答。
- 用户 steer / 干预输入。
- 停止、重试、恢复等操作。

### 7.4 分屏模式

分屏模式用于执行监控和深度干预：

- 上方或左侧展示任务画布。
- 下方或右侧展示当前节点会话。
- Inspector 展示当前节点状态、输入输出契约、运行记录和产物。
- 点击画布节点应联动会话和 Inspector。

## 8. 删除任务要求

删除任务必须删除完整任务数据，而不是只删除主数据。

应覆盖：

- 任务主记录。
- TaskGraph。
- GraphRevision。
- GraphRun。
- NodeRun。
- NodeAttempt。
- TaskEvent。
- 任务会话索引。
- 需求终稿目录。
- 任务产物目录。
- 与任务绑定的本地缓存或索引。

删除前可做用户确认，但确认后不得留下孤儿数据。

## 9. 本轮实现已落地的方向

本轮代码调整围绕“复用会话入口和任务串联”推进，当前实现方向包括：

- 在常规会话输入区增加会话模式和任务模式切换。
- 任务模式入口行为等同于新任务会话，不在当前普通会话上原地切换。
- 任务模式强制切换到 Jishu Agent；未安装时提示。
- 任务模式增加规划 Skill 选择，默认 `Jishu Task Planner`。
- 任务会话发送给 Agent 的任务阶段约束作为隐藏指令注入，用户可见消息保持干净。
- 任务会话列表和常规会话列表按任务归属分离。
- 任务会话列表从 session 维度收敛为任务实例维度，一个任务只显示一条。
- 任务实例记录需求讨论会话、流程规划会话、需求终稿和最终 graph。
- 需求定稿写入项目下固定任务需求目录。
- 需求定稿后自动开启第二轮流程规划会话。
- 流程图创建阶段使用需求终稿和流程规划阶段会话作为输入。
- 任务页面继续承接流程图、Revision、运行与会话联动。

这些调整仍应继续接受实际测试验证，尤其是：

- 常规会话修复是否能自动覆盖任务模式。
- 任务模式下交互式问答和引导发送是否完整复用。
- 工具调用卡片在任务模式下是否和常规会话一致。
- 需求终稿内容是否足以支撑流程创建。
- 任务删除是否完整清理关联数据。

## 10. 后续验收清单

### 10.1 任务发起

- 从 `新任务` 进入后，页面外观接近新对话。
- 输入框内显示任务模式。
- 任务模式默认选中 `Jishu Task Planner`。
- 任务模式自动使用 `Jishu Agent`。
- 未安装 Jishu Agent 时不能继续发送，并有明确提示。

### 10.2 真实会话复用

- 任务模式发送消息后，是真实智能体回复，不是写死回复。
- 常规会话支持的交互式问答在任务模式可用。
- 常规会话支持的引导发送在任务模式可用。
- 常规会话支持的工具渲染在任务模式可用。
- 停止会话按钮有效，停止后仍可继续交流。

### 10.3 需求定稿

- 需求讨论完成后，会话内出现是否生成流程图的交互。
- 用户确认后生成需求终稿。
- 需求终稿写入固定目录。
- 需求终稿内容不包含隐藏指令。
- 需求终稿能被后续流程创建读取。

### 10.4 流程创建

- 简单任务可一句话直接进入流程规划阶段会话。
- 复杂任务可多轮讨论后进入流程规划阶段会话。
- 流程规划阶段仍复用会话能力，用户可打断、交互式问答和继续补充。
- 用户在流程规划阶段确认后，再生成流程图。
- 生成流程后进入任务画布页面。
- 会话区域能显示前面需求讨论和规划输出，不应丢失或错位。
- 输入框和会话内容宽度一致。

### 10.5 执行干预

- 点击节点不会报错。
- 节点 Inspector 能展示职责、状态、输入输出和执行记录。
- 节点会话能查看执行过程。
- 用户可以在节点运行中干预或引导。

### 10.6 数据清理

- 删除任务后，任务列表不再出现。
- 任务图、运行记录、事件、会话索引、需求终稿和产物目录均被清理。
- 不留下孤儿任务数据。
