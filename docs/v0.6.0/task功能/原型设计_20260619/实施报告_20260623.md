## 二、后端改动

### 文件
- `src-tauri/src/task_launch.rs`（重写）
- `src-tauri/src/lib.rs`（命令注册）

### 关键改动
1. **存储迁移**：JSON 文件 → 独立 SQLite（`.jishu-hub/tasks/task-instances.db`，WAL 模式，schema version 1）
2. **TaskLaunchInstance 字段扩充**：
   - 新增 `planner_agent_id`（默认 "jishu_agent"）
   - 新增 `active_run_id` / `last_run_id` / `run_status`（执行实例关联）

   - `status` 收敛为 4 值：requirements_discussing / requirements_finalized / planning_discussing / graph_created（终态）
   - `run_status` 独立 5 值：running / paused / completed / failed / cancelled
   - 状态机止步 graph_created，执行态由 run_status 追踪
   - cancelled 流转补全（running/paused → cancelled）
4. **normalize_phase 统一 canonical 为 "execution"**（消除 "graph" 别名）
5. **finalize_requirement 接口简化**：改为 `RequirementFinalizeRequest` 单一入参（`requirement_markdown` + `creation_mode`），终稿格式交给调用方（skill 约束），不再硬编码 render_requirement_markdown
6. **新增命令**：
   - `task_launch_sync_run_status`（前端轮询 run 状态后回写）
   - `task_launch_get_instance`（查单个任务实例）
   - `task_launch_create_from_existing_graph`（孤儿 graph 补建 TaskInstance）

## 九、Pi(Jishu Agent) 会话恢复修复

### 问题
Pi 进程重启后（或首次打开已有会话），新启动的 Pi 进程不恢复之前的会话历史，agent 像新会话一样不记得上下文。

### 根因
Jishu Agent 的 `build_acp_command` 启动 Pi 时只传 `--mode rpc`，没有传 session_id。Pi 每次都创建全新 session，丢失历史。而 `prepare_gui_turn` 已经把真实 session_id 放到了 `ChatRequest.session_id`，只是 `build_acp_command` 忽略了它（参数名 `_req`）。

### 修复
- `src-tauri/src/agent/jishu_self/mod.rs`：`build_acp_command` 接收 `req`（不再忽略），当 `req.session_id` 存在时加 `--session-id <id>` 参数，让 Pi 恢复指定会话
- Pi 的 `--session-id` 语义：精确 project session id，存在则恢复，不存在则创建
- 对比：Claude/OpenCode(ACP) 通过 session/resume 恢复，Pi 通过 --session-id 恢复
- 提交：71f73abb

## 十二、阶段推进机制重构（核心）

### 问题演进

阶段推进经历了三次架构演进：

#### 第一版：前端关键词检测（已废弃）
- `isGenerateTaskConfirmation` 检测 agent 交互问答回复中的"生成/流程/确认"关键词
- **问题**：不可靠，换 skill 话术就可能失效，永远存在遗漏可能

#### 第二版：前端关键词 + 后端 task_advance_phase（过渡）
- 后端新增 `task_advance_phase` 命令（`task_launch.rs`）
- 前端仍用关键词检测，但推进逻辑走后端命令
- **问题**：仍然依赖关键词检测，没解决根本问题

#### 第三版（最终）：agent 调 jishu-cli 触发（当前架构）
- **agent 主动调用 `advance_phase.mjs` 触发阶段推进**，不依赖前端猜意图
- 前端只做状态变化检测 + 用户确认弹窗

### 最终架构

```
agent 判断需求收敛
    ↓
bash 执行 advance_phase.mjs --session xxx --phase planning
    ↓
advance_phase.mjs → jishu-cli task find --session xxx → task_id
    ↓
jishu-cli task advance --task-id xxx --phase planning
    ↓
jishu-cli 直接调 task_launch::advance_phase（共享 SQLite 库）
    ↓
SQLite 状态确定性推进（requirements_finalized → planning_discussing）
    ↓
前端 turn_complete 后刷新实例，对比 status 值（确定性检测）
    ↓
弹窗"需求讨论阶段完成，是否进入规划？" → 用户确认
    ↓
确认后 advanceToPhase 发起规划阶段新会话
```

### 关键特性
- **agent 主动触发**：agent 通过 skill 知道何时该推进，主动调 advance_phase.mjs
- **确定性**：jishu-cli 直接操作 SQLite，不依赖文本/关键词
- **人在环里**：前端检测到状态变化后弹窗，用户确认才真正进入下一阶段
- **skill 无关**：推进机制完全独立于 skill 内容，换 skill 也能正常工作
- **多任务不混淆**：session_id 唯一映射 task_instance

### 涉及文件与提交

## 十三、jishu-task-planner skill 重构

### 问题
1. 原 SKILL.md 只有角色 manifest，没有方法论指导，agent 不知道怎么做
2. skill 没有被 Pi 正确加载（装在 `~/.jishu-agent/task-plan/`，但 Pi 只从 `~/.jishu-agent/skills/` 加载）
3. 所有内容塞在一个 MD 文件，不符合 skill-creator 规范

### 修复

#### skill 结构（按 skill-creator 规范）
```
jishu-task-planner/
├── SKILL.md                           ← 精简骨架(三阶段核心流程 + 指向 scripts/references)
├── scripts/
│   ├── format_requirement.mjs         ← 需求终稿格式化(agent 调用 → 确定性产出标准格式)
│   ├── format_flow_plan.mjs           ← 流程方案格式化(agent 调用 → 确定性产出节点方案)
│   └── advance_phase.mjs             ← 阶段推进(agent 调用 → jishu-cli task advance)
└── references/
    ├── requirements-phase.md          ← 需求讨论阶段详细指导(对话节奏/收敛判断/脚本参数)
    └── planning-phase.md              ← 流程规划阶段详细指导(节点设计/确认流程)
```

#### Pi skill 加载修复
- `task_plan.rs` 安装时调 `link_to_pi_skills_dir`，在 `~/.jishu-agent/skills/<skill_id>` 创建符号链接
- Pi 从 `skills/` 目录加载 skill，agent 能在 skill 列表里识别到 jishu-task-planner
- Windows fallback：符号链接失败时复制目录

#### 安装逻辑增强
- `copy_bundled_extra_files`：安装时复制 scripts/references/assets 子目录（不再只写 SKILL.md）
- `bundled_dir_entries`：编译时 `include_bytes!` 嵌入额外文件
- Jishu Agent 安装时自动安装 jishu-task-planner skill（不再需要手动安装）

#### SKILL.md 核心方法论
- **三条核心原则**：每次只问一个核心问题、简洁回应不做大段独白、尊重用户节奏
- **阶段推进的唯一触发方式是执行 advance_phase.mjs**，只在文本里说"完成了"不会推进
- `request_user_input` 正确用法：question 一句话 + options 2-4 个字符串
- 用户说"你定/以你的理解为准"时直接给完整方案 + 总确认

#### 开发模式 cli 支持
- `build_acp_command`（debug 模式）自动注入 `JISHU_CLI_BIN` 指向 `target/debug/jishu-cli`
- advance_phase.mjs 支持 `JISHU_CLI_BIN` 环境变量覆盖 cli 路径
- release 模式不设（自动 fallback 到 PATH 的安装版）
